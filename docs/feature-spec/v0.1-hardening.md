# Feature Specification: Gestalt v0.1 Harness Stabilization

## 1. Summary

Gestalt v0.1 should become a small, stable, malleable, embeddable harness that
can support clients and products without absorbing their workflows or user
interfaces.

The release objective is:

> Stabilize Gestalt's execution guarantees and its product-neutral embedding
> boundary while keeping implementation details and optional integrations free
> to evolve.

This is a contract-maturity release, not a feature-expansion release.

The primary outcomes are:

1. Harness execution invariants are explicit and test-covered.
2. Embedders use a narrow, product-neutral host API instead of runtime
   internals.
3. Client DTOs, persisted formats, CLI output, and Rust APIs have separate
   compatibility policies.
4. Context, policy, approval, trace, and extension behavior remain observable
   and auditable.
5. Existing documentation is classified, simplified, and assigned clear
   authority.
6. Pre-hardening compatibility paths and deprecated experimental APIs are
   removed before the stable v0.1 contract is declared.

## 2. Document Authority

This document owns the scope and release criteria for v0.1 hardening. It does
not override accepted architecture decisions.

Authority is resolved in this order:

1. Accepted ADRs govern architectural decisions.
2. Versioned v0.1 contract documentation governs released interfaces and
   persisted formats.
3. This feature specification governs v0.1 hardening scope.
4. Domain feature specifications govern proposed domain behavior where they do
   not conflict with accepted ADRs.
5. Implementation plans govern execution only; they do not create architecture.
6. The PRD and architecture overview provide vision, principles, and historical
   context.

Conflicts with accepted ADRs must be resolved by superseding or amending the
ADR before implementation. A phase plan may not silently change an accepted
decision.

The repository-wide documentation taxonomy and migration policy are defined in
[`docs/README.md`](../README.md).

## 3. Product Philosophy Alignment

The v0.1 design follows these product principles.

### 3.1 The harness owns execution guarantees

Gestalt owns capabilities that improve safe, repeatable, observable,
controllable, and provider-neutral model execution:

- provider normalization;
- context construction;
- tool validation and execution;
- policy and approval;
- session and run control;
- event production and trace persistence;
- replay and generic verification;
- runtime composition and extension isolation.

### 3.2 Products own intent and presentation

Hosts and products own:

- workflow strategy;
- domain behavior;
- product-specific approval UX;
- navigation and presentation;
- scheduling and collaboration;
- vertical-specific reports;
- agent topology and business logic.

No Workbench-, Tauri-, Ratatui-, terminal-, or remote-platform-specific type may
appear in a stable harness contract.

### 3.3 The loop remains small

New client APIs, persistence formats, extensions, and diagnostics must not add
product concerns to `AgentLoop`. They belong in runtime composition, app
services, adapters, or projections.

### 3.4 Events remain the ground truth

Runtime behavior originates from one canonical event-producing execution path.
Trace records and client events may use different versioned representations,
but they must be projections of that same source rather than independent
logging paths.

### 3.5 Explicit authority

Every tool, regardless of origin, passes through validation, policy, approval,
execution, output shaping, trace, and canonical result recording. Package or
tool metadata requests authority; it never grants authority.

### 3.6 Deterministic and explainable context

For identical declared inputs and captured contributions, context construction
produces identical ordered outputs and hashes. Dynamic contributions are
attributed, captured, and hashed so replay does not depend on repeating an
external side effect.

## 4. Goals

### 4.1 Product goals

1. A third-party Rust host can embed Gestalt without importing internal runtime
   modules.
2. CLI and TUI remain clients of reusable app/runtime services.
3. Future local or remote hosts can implement the same semantic control
   contract.
4. Tools and extensions remain malleable without polluting `gestalt-core`.
5. Users and contributors can identify which documents and contracts are
   authoritative.

### 4.2 Architecture goals

1. Preserve `gestalt-core` as I/O-free and provider-neutral.
2. Keep execution policy and audit paths canonical.
3. Separate core models from client DTOs and persisted wire formats.
4. Make runtime composition inspectable and fingerprinted.
5. Make context projection deterministic and replayable.
6. Make extension activation structured, permissioned, and fail-safe.
7. Keep `gestalt.json` strict, documented, and versioned.
8. Provide a deliberately small stable CLI automation surface.

### 4.3 Documentation goals

1. Replace implicit document authority with a documented hierarchy.
2. Reduce the PRD and architecture monoliths to durable vision and overview
   material.
3. Move accepted decisions into standalone ADRs.
4. Harden domain documents around contracts and invariants rather than source
   snapshots.
5. Mark completed, superseded, historical, and proposed documents explicitly.
6. Preserve useful history without allowing old plans or examples to masquerade
   as current behavior.

## 5. Non-Goals

v0.1 hardening does not require:

1. A Workbench implementation or Workbench adapter in this repository.
2. A remote runner or task-bundle protocol.
3. A marketplace or package registry.
4. Enterprise tenancy.
5. Multi-agent orchestration as a default path.
6. A complete connector, MCP, skill, or extension ecosystem.
7. OS-level sandboxing beyond the explicitly documented v0.1 execution
   boundary.
8. A visual workflow builder.
9. A client/product extension runtime.
10. Rewriting every historical document during this feature.
11. A no-op configuration migration command for schema version 1.
12. Compatibility with unreleased pre-hardening configuration, extension,
    Rust API, or persisted formats.

## 6. Current-State Assessment

Gestalt already has the correct high-level crate split:

```text
gestalt-core
    Pure harness contracts and orchestration.

gestalt-runtime
    Concrete execution and runtime composition.

gestalt-app
    Reusable application services.

gestalt-cli / gestalt-tui
    Presentation shells.
```

The main gaps are contract classification and boundary semantics:

- `gestalt-runtime` publicly exports many implementation modules.
- Existing `RuntimeControl` and `HostControl` divide host operations
  inconsistently.
- `RuntimeHost::new` can panic when startup extension activation fails.
- raw `AgentEvent` is used directly by the current trace envelope.
- the CLI already has a JSON envelope that differs from the one previously
  proposed by this specification.
- accepted extension ADRs and proposed extension documents describe overlapping
  maturity states.
- legacy TOML configuration, deprecated JSON aliases, extension manifest V1
  adapters, deprecated Rust APIs, and pre-hardening persistence compatibility
  remain active in code and tests.
- documentation contains large monoliths, stale crate references, and
  overlapping plans/specifications without a repository-wide authority map.

## 7. Contract and Stability Model

### 7.1 Contract classes

Gestalt must classify contracts by audience and compatibility mechanism.

| Class | Purpose | Examples | Compatibility mechanism |
|---|---|---|---|
| Execution invariant | Behavior all implementations preserve | policy before execution | invariant and conformance tests |
| Rust embedding API | In-process host construction and control | builders, host façade | Rust API compatibility |
| Authoring SPI | Interfaces implemented by integrators | tool/provider authoring | narrow traits, defaults, adapters |
| Client DTO | Product-neutral control and observation | session requests, event projections | explicitly versioned DTOs |
| Persisted contract | Durable replay/resume data | trace, run manifest, context artifacts | schema version and migration |
| CLI contract | Automation behavior | command JSON and exit codes | snapshots and compatibility policy |
| Internal model | Runtime implementation | raw session/projection/registry state | no compatibility promise |

The same Rust type must not be assumed to serve all classes.

### 7.2 Stability tiers

```text
Stable v0.1
    Backward-compatible throughout v0.1.x.

Experimental v0.1
    Publicly usable but explicitly carries no v0.1.x compatibility promise.

Internal
    No external compatibility promise even if temporarily public in Rust.

Versioned contract
    Evolves through explicit versioning, compatibility readers, or migration.
```

### 7.3 Stable surface policy

v0.1 stabilizes narrow modules and documented exports, not entire crates.

Candidate stable surfaces are:

- documented execution invariants;
- the supported runtime construction path;
- the product-neutral host-control API and client DTO module;
- the minimum supported tool-authoring SPI;
- selected app-service report and request types;
- versioned trace, run-manifest, and context-diagnostic schemas;
- the selected CLI automation subset and its existing or deliberately migrated
  JSON envelope;
- `gestalt.json` schema version 1.

The following remain internal or experimental unless H0 produces a specific
contrary decision:

- `AgentLoop` construction details;
- raw `Session` and raw `AgentEvent` as client contracts;
- `ContextPacket`, `PreparedContext`, and projection implementation types as
  client contracts;
- registry and extension-manager internals;
- compaction algorithms and heuristics;
- provider-native types;
- hot reload and orchestration helpers.

### 7.4 Public Rust API rules

1. Public fields are reserved for passive DTOs.
2. Invariant-bearing types use constructors or builders.
3. Extensible public enums and structs use appropriate forward-compatibility
   patterns before stabilization.
4. Stable IDs use domain newtypes where accidental interchange is dangerous.
5. Stable traits document error, cancellation, concurrency, and panic behavior.
6. A technically public item may be documented as internal during v0.1
   preparation, but stable documentation must export only the supported path.

### 7.5 Greenfield compatibility cutoff

Pre-hardening v0.1 is an unreleased development line. It has no compatibility
claim. Backward-compatibility obligations begin with the stable v0.1 release,
not with experimental behavior that existed before hardening.

This cutoff does not remove current version identifiers:

- `gestalt.json` schema version 1 remains the canonical configuration format;
- extension package manifest version 2 remains the canonical extension format;
- versioned v0.1 trace and client contracts remain version 1 where specified.

It removes obsolete alternatives and adapters that predate those canonical
formats.

#### CLEAN-001: Remove legacy harness configuration files

The following user configuration files are unsupported:

```text
<workspace>/.gestalt/config.toml
<workspace>/.gestalt/policies.toml
<global-config>/gestalt/config.toml
```

When any known legacy harness configuration file is encountered during config
discovery, loading, mutation, or diagnostics, Gestalt returns:

```text
UNSUPPORTED_LEGACY_CONFIG
```

The error includes the legacy path and the supported `gestalt.json` path. The
file is not parsed, merged, migrated, seeded, renamed, or deleted. Detection is
allowed only to fail safely; no compatibility behavior remains.

The same `UNSUPPORTED_LEGACY_CONFIG` code is preserved in app-service and CLI
JSON error projections. Human-readable output may add remediation text but must
not substitute a generic config error code.

`gestalt.extension.toml` is not a legacy harness configuration file. It remains
the canonical TOML package-manifest filename and must use manifest version 2.

#### CLEAN-002: Remove deprecated configuration aliases

Remove deprecated fields and normalization paths, including:

```text
context.workspace_file
context.memory_file
policies.bash.yolo_allow
policies.bash.always_confirm
policies.bash.always_deny
legacy secret: credential references
legacy extension trust/config aliases identified by H0
```

The Rust config model and generated JSON Schema must not contain these fields.
Because `gestalt.json` is strict, deprecated fields fail as unknown or invalid
configuration; they are not normalized into current fields.

#### CLEAN-003: Reject extension manifest and protocol V1

Extension manifest V1 and the V1 process-extension protocol are unsupported.

Gestalt must:

- require `manifest_version = 2`;
- reject absent, malformed, or V1 manifest versions before activation;
- never infer protocol 1.0;
- remove V1-to-V2 package conversion and legacy component variants;
- remove V1 builder, discovery, launch, and broker adapter paths;
- remove V1 compatibility tests and replace them with rejection tests.

The Lifecycle Protocol V2, command tools, and MCP-backed tools remain supported.
An internal process transport may remain when used by current V2 capabilities;
it must not expose or route a V1 compatibility contract.

#### CLEAN-004: Remove deprecated Rust APIs

H0 inventories and removes every production `#[deprecated]` API and supporting
adapter that predates the stable v0.1 surface. This includes the known:

- builder `middleware` path;
- `RuntimeRegistry` alias;
- deprecated provider-registry constructors;
- `GestaltExtension` trait and compatibility bridge.

Production crates and their tests must not use crate-wide or module-wide
`allow(deprecated)` to preserve pre-hardening APIs.

#### CLEAN-005: Remove pre-hardening persistence compatibility

H0 inventories trace, run-manifest, context-artifact, and checkpoint readers
that exist only for pre-hardening formats. H2 removes those compatibility
readers and migration branches.

Stable v0.1 readers only promise compatibility with formats published by the
stable release. Unsupported pre-hardening data fails through the current
incompatible-version/error path; it is not migrated.

#### CLEAN-006: Remove compatibility claims and fixtures

Active guides, READMEs, schemas, examples, and fixtures must describe only the
greenfield v0.1 contracts. Historical migration documents may be archived, but
must not be linked as an active supported path.

Tests that previously proved fallback or compatibility are deleted or inverted
to prove rejection and absence.

#### CLEAN-007: Maintain a removal ledger

H0 creates a checked removal ledger covering:

- production code and public exports;
- Cargo dependencies used only by removed compatibility paths;
- JSON Schema fields;
- config and extension fixtures;
- CLI/TUI diagnostics;
- tests and compile-time deprecation allowances;
- active guides, migrations, and examples;
- accepted ADR clauses that require amendment or supersession.

Every item has an owning phase and an absence check. The ledger is complete
only when repository-wide discovery finds no unclassified deprecated or legacy
compatibility behavior.

## 8. Documentation Hardening

### 8.1 Required documentation layers

The maintained documentation set should converge on:

```text
README.md
    User-facing project entry point.

docs/README.md
    Documentation map, authority, lifecycle, and ownership.

docs/v0.1/
    Released contract documentation for v0.1.

docs/adrs/
    Accepted and superseded architectural decisions.

docs/feature-spec/
    Proposed or active domain changes.

docs/plans/
    Time-bounded implementation plans.

docs/guides/ or existing named guides
    Task-oriented user and extension-author guidance.

docs/audits/, docs/solutions/, docs/migrations/
    Evidence, historical findings, and migrations.

docs/archive/
    Superseded documents retained for history.
```

### 8.2 DOC-001: Maintain a repository documentation index

`docs/README.md` must define:

- authority order;
- document types;
- lifecycle statuses;
- owner expectations;
- the current canonical document for each domain;
- the disposition of existing documents;
- archive and redirect rules.

### 8.3 DOC-002: Create the v0.1 contract map

Create `docs/v0.1/README.md` during H0. It must link to the released contracts
for:

- embedding and host control;
- app services;
- context diagnostics;
- trace and run manifests;
- configuration;
- policy and approval;
- extensions;
- CLI automation.

Only implemented, test-backed behavior belongs in `docs/v0.1/`.

### 8.4 DOC-003: Simplify the PRD

`docs/gestalt-harness-prd.md` should retain:

- product vision;
- target users and problems;
- philosophy and product principles;
- scope boundaries;
- release-level priorities and success measures.

Move or remove:

- Rust type definitions;
- endpoint- or trait-level contracts;
- source-tree snapshots;
- duplicated CLI/config schemas;
- accepted architecture decisions;
- implementation task lists.

The PRD must link to domain contracts rather than restating them.

### 8.5 DOC-004: Simplify the architecture monolith

`docs/gestalt-harness-architecture.md` should become a current architectural
overview:

- system and crate boundaries;
- canonical execution flow;
- trust and authority boundaries;
- major component relationships;
- links to accepted ADRs and domain contracts.

ADRs 001-022 currently embedded in the monolith should be extracted into
standalone ADR files before their source sections are removed. New decisions
must not be added to the monolith.

Code listings that mirror current structs or traits should be replaced with
short conceptual contracts and links to versioned API documentation.

### 8.6 DOC-005: Harden domain specifications

Every active domain specification must:

1. Have valid metadata with `status`, `type`, `target`, and owners.
2. Declare whether it is normative, proposed, implemented, superseded, or
   historical.
3. Identify accepted ADRs that constrain it.
4. State invariants, public contracts, non-goals, failure behavior, and
   acceptance criteria.
5. Avoid treating source-code snapshots as durable requirements.
6. Avoid stale crate names after crate consolidation.
7. Link to one implementation plan rather than embedding an unbounded task
   backlog.

Overlapping context specifications must be reconciled around a single context
architecture contract. Overlapping extension documents must treat ADR-028
through ADR-031 as authoritative and distinguish package, lifecycle protocol,
manifest, and author-guide concerns.

### 8.7 DOC-006: Classify plans, audits, and historical documents

- Plans record intended execution and completion status; they do not define
  architecture.
- Audits record evidence at a point in time and must include an audit date.
- Solution documents record resolved findings and link to the enforcing tests
  or ADRs.
- Completed or abandoned plans are marked accordingly and may be archived.
- Moving a document must leave a short redirect at its old path when external
  or repository links would otherwise break.

### 8.8 DOC-007: Rationalize the existing documentation in stages

The documentation migration is staged:

```text
D0 Inventory
    Assign type, owner, status, authority, and domain.

D1 Authority
    Fix metadata and declare canonical documents and ADR constraints.

D2 Decision extraction
    Move accepted decisions from monoliths/specs into standalone ADRs.

D3 Monolith reduction
    Reduce the PRD, architecture, and roadmap to their durable roles.

D4 Domain hardening
    Consolidate overlapping specs and remove stale source snapshots.

D5 Archive
    Archive superseded plans/specs with redirects and link validation.
```

This migration must be incremental. A bulk deletion or move is not acceptable
without link checks and a verified replacement.

### 8.9 DOC-008: Document public boundaries per crate

Each crate README should state:

- what the crate owns and must not own;
- supported stable entry points;
- experimental and internal modules;
- construction examples;
- failure and cancellation semantics;
- feature-gate effects.

## 9. Product-Neutral Runtime Control

### 9.1 Purpose

The stable host boundary allows clients to control and observe the harness
without mutating runtime registries, canonical session history, or provider
adapters.

It is a semantic contract first and an in-process Rust façade second. Future
transports may implement the same semantics, but the Rust trait itself is not a
wire protocol.

### 9.2 Capability structure

Use narrow capability interfaces and expose a convenience façade:

```text
SessionControlV1
    start, send, cancel, inspect session

RunQueryV1
    list and inspect runs

ApprovalControlV1
    respond to pending approvals

EventSourceV1
    subscribe or resume from a cursor

ArtifactAccessV1
    list, describe, and read bounded artifact content

RuntimeInspectionV1
    inspect runtime composition and health

ExtensionAdmin
    reload and extension administration; experimental in v0.1
```

`RuntimeControlV1` may aggregate the stable capabilities for ergonomic
in-process use. Capability separation allows minimal and remote hosts to expose
only supported behavior.

### 9.3 RUNTIME-001: Use versioned product-neutral DTOs

Requests, responses, IDs, errors, cursors, and event projections are versioned
DTOs separate from:

- raw `Session`;
- raw `AgentEvent` and `RuntimeEvent`;
- `RuntimeConfig`;
- provider-native structures;
- registry and artifact-store implementations.

### 9.4 RUNTIME-002: Define session and message semantics

The contract must specify:

- host- versus caller-assigned IDs;
- start, continue, resume, and branch behavior;
- whether message submission is queued or synchronous;
- idempotency keys;
- concurrent-send behavior;
- queue bounds and backpressure;
- acknowledgement and completion events;
- cancellation target and race behavior.

The v0.1 implementation should preserve the existing steering queue model
instead of inventing a second message path.

### 9.5 RUNTIME-003: Define event subscription semantics

The contract must specify:

- cursor shape and scope;
- ordering domain;
- replay from retained history;
- broadcast lag behavior;
- filtering;
- terminal events;
- reconnect behavior;
- redaction.

An in-memory broadcast receiver is an implementation detail, not the stable
contract.

### 9.6 RUNTIME-004: Define bounded artifact access

Artifact DTOs use logical artifact IDs or URIs and workspace-relative display
paths. They include size, media type, and integrity metadata.

Reads must be bounded or streamed. A stable API must not require loading an
unbounded artifact into one byte vector.

### 9.7 RUNTIME-005: Define stable errors

Stable operations return a versioned error classification with:

- stable code;
- human-readable message;
- retryability;
- optional structured details;
- correlation identifiers where available.

Internal Rust error chains remain available to in-process diagnostics but are
not serialized directly.

### 9.8 RUNTIME-006: Implement at the host boundary

The full control API is implemented by session-owning hosts, remote clients, and
test doubles. `AgentRuntime` may implement narrow inspection or execution
capabilities, but it is not required to implement session, run, and artifact
hosting that it does not own.

### 9.9 APP-001: Keep `gestalt-app` product-neutral

`gestalt-app` owns reusable application services such as:

- config and workspace resolution;
- provider/profile/model services;
- runtime construction;
- runs and sessions;
- reports and diagnostics.

It must not contain `WorkbenchRuntimeService` or assumptions about a specific
UI framework. Product-specific adapters live in their product repositories.

### 9.10 APP-002: Return structured diagnostics

App services return warnings and diagnostics as data. CLI and other clients
decide how to render them. Direct presentation writes from reusable service
paths must be removed or isolated behind a caller-provided diagnostic sink.

## 10. Core Primitive Hardening

### 10.1 CORE-001: Freeze behavior before representation

v0.1 freezes core execution invariants before freezing raw core models.

Required invariants include:

1. Context is prepared before a provider request.
2. Provider-native streams are normalized before entering the loop.
3. The complete assistant turn is committed before tool execution.
4. Every tool call passes validation, policy, and any required approval.
5. Tool results are recorded in canonical history.
6. Checkpoints are emitted at documented safe boundaries.
7. Steering messages drain only at safe turn boundaries.
8. Cancellation is observed during context, model, hook, and tool phases.
9. Trace failures follow an explicit fail/degrade policy.

### 10.2 CORE-002: Preserve canonical identity

- Canonical history is append-only during normal execution.
- Message identity is stable within a session lineage.
- Projection and compaction do not delete canonical history.
- Continue, resume, and branch preserve documented lineage metadata.

### 10.3 CORE-003: Audit stable SPIs separately

The provider, tool, policy, approval, context, and trace traits must each be
classified as one of:

- supported external SPI;
- runtime-internal interface;
- experimental extension point.

Do not stabilize a trait merely because it is currently `pub`.

### 10.4 CORE-004: Document failures and panics

Every stable Rust method documents validation, policy, approval, provider, tool,
trace, cancellation, context-exhaustion, and panic behavior where applicable.
Library construction and execution paths must not panic on expected input or
activation failures.

## 11. Context Contract Hardening

### 11.1 CTX-001: Stabilize invariants and projections

Stable:

- canonical-versus-projected history invariant;
- message identity and lineage behavior;
- versioned context diagnostic DTO;
- versioned persisted manifests required for replay/resume;
- source, omission, trust, and authority reporting.

Internal or experimental:

- `PreparedContext`;
- projection planning structs;
- prompt-cache implementation structs;
- compaction and tool-clearing algorithms;
- token-estimation implementation;
- summarization strategy.

### 11.2 CTX-002: Determinism includes captured contributions

The determinism input set includes:

- canonical session history;
- context policy;
- provider/model capability snapshot;
- runtime and tool-catalog fingerprint;
- workspace snapshot;
- ordered contributor identities, versions, configuration, and outputs.

Dynamic contributor outputs are captured and hashed. Replay consumes the
captured output unless explicitly running a non-deterministic live replay mode.

### 11.3 CTX-003: Stable context diagnostics

Clients receive a `ContextBuildReportV1`-style DTO containing:

- session, run, and turn identity;
- packet and pipeline identity;
- token estimate and tokenizer identity;
- ordered sources and omissions;
- trust and authority metadata;
- pressure classification;
- captured-contribution hashes;
- prompt-source and projection references where available.

Clients do not parse raw checkpoint or projection internals.

### 11.4 CTX-004: Context contributors are bounded

Contributors:

1. return bounded typed contributions;
2. declare stability and authority;
3. have deterministic ordering and conflict rules;
4. cannot mutate canonical session history;
5. expose enough identity to fingerprint their contribution.

## 12. Configuration Hardening

### 12.1 CFG-001: Keep schema version 1 strict

Unknown fields remain errors. Schema and Rust model parity is test-covered.
Schema version 1 is the first supported stable schema; deprecated pre-hardening
aliases are not part of it.

### 12.2 CFG-002: Classify sections

Every top-level section is documented as stable, experimental, client-specific,
or internal. A section may contain fields of different maturity only when those
fields are individually labeled.

The `tui` section is client-specific and does not establish precedent for
product configuration in the runtime schema.

### 12.3 CFG-003: Formalize layering and provenance

The documented precedence remains:

```text
built-in defaults
< global gestalt.json
< workspace gestalt.json
< supported GESTALT_* environment overrides
< CLI flags
```

Config explanation reports the source of each effective value without exposing
raw secrets.

### 12.4 CFG-004: Define migration policy without a no-op command

v0.1 must:

- reject unsupported schema versions clearly;
- preserve version 1 readers and fixtures;
- document how a future migration is registered and tested.

A migration command is introduced only when a second schema version exists.
Pre-hardening TOML configuration is not a prior schema version and is not a
migration source. Known legacy files fail with `UNSUPPORTED_LEGACY_CONFIG`
without parsing or migration as required by CLEAN-001.

### 12.5 CFG-005: Keep product config outside runtime config

Do not add a Workbench namespace to `gestalt.json` during v0.1 hardening.
Products may maintain their own configuration or propose a generic host
namespace through a separate specification.

## 13. Extension Hardening

### 13.1 Authority and status

ADR-028 through ADR-031 are authoritative for extension package components,
runtime snapshots, Lifecycle Protocol V2, and the greenfield compatibility
cutoff. The product-neutral extension spec remains a broader evolution document
and must not downgrade implemented accepted decisions implicitly.

### 13.2 EXT-001: Publish a component-level stability matrix

Classify separately:

- package and manifest validation;
- configured instances;
- Lifecycle Protocol V2;
- command tools and MCP-backed tools;
- context providers and policy guards;
- reload;
- client/product descriptors;
- package lock and remote launchers.

Do not label the entire extension architecture stable or experimental as one
unit.

Manifest and protocol V1 are outside the stability matrix because CLEAN-003
removes them before v0.1 stabilization.

### 13.3 EXT-002: Preserve canonical authority

Effective authority is:

```text
package request
∩ user/workspace grant
∩ host policy
∩ managed policy when present
∩ runtime execution policy
```

Trust decisions are integrity-aware. Deprecated ID-only trust entries are
removed under CLEAN-002 rather than retained as compatibility behavior.

### 13.4 EXT-003: Replace startup panics with structured policy

Runtime host construction returns a structured result and activation report.

Failure behavior depends on criticality:

- required security or policy components fail closed;
- required general components fail host construction;
- optional components may degrade with structured diagnostics;
- reload failure preserves the active generation.

There is no blanket `DegradeAndContinue` default for required components.

### 13.5 EXT-004: Resolve generation pinning before H4

ADR-029 and the current runtime pin a generation lease for a run. The
product-neutral extension spec describes one generation per turn.

Before H4, an ADR must select and define:

- the pinning unit;
- adoption boundaries;
- behavior for multi-turn `run_prompt`;
- reload visibility;
- trace and inspection metadata.

H4 implements the accepted decision rather than choosing it.

### 13.6 EXT-005: Keep client components outside runtime execution

Client/product descriptors may be inventoried, but v0.1 does not execute
arbitrary client code. Clients cannot execute tools, mutate session history,
modify snapshots, bypass policy, or access provider adapters directly.

## 14. Event, Trace, and Replay Hardening

### 14.1 EVT-001: Separate three representations

Define:

1. An internal canonical event record carrying execution metadata.
2. A lossless versioned trace representation for replay and audit.
3. A stable client projection for UI and automation.

All three originate from the same event-producing execution path.

### 14.2 EVT-002: Project from a metadata-bearing record

The client projector consumes a record that already has sequence, timestamp,
runtime generation, session, run, and turn metadata.

`TryFrom<AgentEvent>` alone is insufficient because raw agent events do not
contain all envelope metadata and exclude runtime-level events.

### 14.3 EVT-003: Use typed event payloads

Stable event kinds have typed, versioned payload DTOs or an equivalent schema
registry. A bare `serde_json::Value` payload without per-kind schema and
compatibility rules is not a sufficient stable contract.

Unknown event kinds must have documented reader behavior.

### 14.4 EVT-004: Version persisted formats independently

At minimum:

```text
trace envelope
run manifest
context projection manifest
compaction checkpoint
client event envelope
```

Each format defines:

- version location;
- additive versus breaking changes;
- unknown-field and unknown-kind behavior;
- minimum supported reader behavior;
- migration or compatibility-reader policy.

### 14.5 EVT-005: Add compatibility fixtures

Fixtures cover:

- text response;
- allowed, denied, and approval-gated tools;
- context pressure and compaction;
- artifact spillover;
- cancellation in major phases;
- extension rejection;
- continue, resume, and branch;
- unknown additive fields and event kinds.

Golden comparisons normalize timestamps, generated IDs, and other intentional
nondeterminism rather than freezing incidental values.

## 15. Policy and Approval Hardening

### 15.1 POL-001: Stable client policy projection

The client DTO includes tool call identity, canonical tool identity, input hash,
risk, execution mode, decision, reason, matched rule, and policy source.

Internal policy request or engine types are not automatically client contracts.

### 15.2 POL-002: Stable approval lifecycle

The contract defines:

- approval ID and tool-call correlation;
- rendered summary and editable-input semantics;
- original and edited input hashes;
- expiry and cancellation;
- duplicate or late response behavior;
- bounded session-grant semantics.

### 15.3 POL-003: No origin-based bypass

Built-in, extension, command, and MCP tools follow equivalent validation,
policy, approval, execution, output, and trace stages.

### 15.4 POL-004: Structured diagnostics

Policy explain/test operations support human-readable and machine-readable
reports through the same app-service data model.

## 16. CLI Hardening

### 16.1 CLI-001: Select a small stable automation subset

H0 must classify commands by actual automation value and maturity. Stable v0.1
should prioritize:

- config validation and explanation;
- workspace inspection;
- provider/profile/model inspection;
- run and trace inspection;
- policy explanation;
- tool and runtime inspection;
- non-interactive run execution where its output is contract-tested.

Interactive commands, destructive maintenance operations, TUI, extension
administration, skills, and verification may remain experimental.

### 16.2 CLI-002: Decide the JSON envelope explicitly

The implementation currently emits:

```json
{
  "schema_version": 1,
  "kind": "runs.inspect",
  "data": {}
}
```

Before freezing CLI output, H0 must choose:

1. keep and document the current envelope; or
2. deliberately migrate to a richer envelope with compatibility notes and
   updated fixtures.

The hardening feature must not accidentally introduce a second envelope.

### 16.3 CLI-003: Freeze errors and exit behavior together

Stable commands define:

- error codes;
- JSON error shape;
- process exit codes;
- stdout/stderr rules;
- warning placement;
- behavior when optional features are disabled.

### 16.4 CLI-004: Snapshot stable commands

Every stable JSON command has normalized snapshot or semantic contract tests.

## 17. Provider and Tool Authoring Contracts

### 17.1 PROV-001: Keep provider-native data behind adapters

The loop and client DTOs do not expose provider-native requests or streams.
Provider adapters normalize capabilities, requests, tool schemas, events, and
usage.

### 17.2 PROV-002: Decide whether provider authoring is a stable SPI

H0 must determine whether downstream provider implementations are supported in
v0.1. If supported, define a narrow authoring SPI with capability evolution and
default-method rules. Otherwise document the current provider trait as
experimental/internal.

### 17.3 TOOL-001: Stabilize the minimum tool-authoring path

The supported tool SPI covers:

- identity and description;
- input schema;
- risk classification;
- parallel-safety declaration;
- bounded execution;
- structured output or error;
- descriptor metadata.

### 17.4 TOOL-002: Keep authority host-owned

Tool annotations describe behavior; they do not grant network, filesystem,
shell, environment, or artifact authority. Effective execution context is
host-derived and policy-bounded.

### 17.5 TOOL-003: Distinguish local SPI from remote DTOs

Path-based `ToolContext` and `ToolOutput::Artifact` may remain appropriate for
in-process worker execution. They are not reused directly as remote or client
DTOs; public DTOs use logical IDs, URIs, and relative display paths.

## 18. Remote Readiness

Remote execution is deferred. v0.1 preserves only constraints that avoid
blocking it:

1. Client DTOs are serializable in principle and do not expose provider-native
   or registry types.
2. Public artifact references are logical IDs or URIs.
3. Secrets are referenced by handles and never serialized into traces,
   manifests, or client DTOs.
4. Event cursors and idempotency are explicit.
5. A future remote run can preserve the same logical policy, event, trace, and
   artifact contracts.

No `TaskBundleV1` is defined until a remote execution model has its own feature
specification and threat model.

## 19. Required Architectural Decisions Before Implementation

H0 must resolve or route these decisions:

| Decision | Resolution mechanism |
|---|---|
| Stable Rust exports and external SPIs | API inventory and stability contract |
| Runtime-control operation semantics | v0.1 control contract |
| Current versus richer CLI JSON envelope | compatibility decision |
| Run-level versus turn-level generation lease | amend or supersede ADR-029 |
| Internal, trace, and client event representations | event/trace contract or ADR |
| Required versus optional extension activation behavior | activation policy contract |
| Greenfield compatibility cutoff and removal ledger | ADR-031 and CLEAN requirements |

No later phase may start with an unresolved decision on which it depends.

## 20. Implementation Phases

Each phase receives a separate plan document under:

```text
docs/plans/v0.1-hardening/
├── H0-contract-inventory-and-decisions.md
├── pre-hardening-removal-ledger.md
├── H1-runtime-control-and-app-boundary.md
├── H2-event-trace-and-context-contracts.md
├── H3-config-and-cli-stability.md
└── H4-extension-minimum-stability.md
```

The feature specification defines scope. Phase plans define execution.

Every phase plan must include:

- requirement IDs covered;
- current-state evidence;
- accepted ADR constraints;
- dependencies and explicit non-goals;
- public API/schema changes;
- compatibility and migration behavior;
- failure and security semantics;
- exact tests and fixtures;
- documentation updates;
- exit criteria;
- rollback or partial-completion handling where relevant.

### Phase H0 — Contract inventory and decisions

Goal: establish authority and decide what v0.1 actually promises.

Scope:

- documentation inventory and metadata;
- `docs/README.md` and `docs/v0.1/README.md`;
- `docs/plans/v0.1-hardening/pre-hardening-removal-ledger.md`;
- ADR amendments required by the removal cutoff;
- deprecated Rust API and public-export removal where it is not coupled to a
  later domain migration; all remaining items receive a phase owner;
- Rust API and SPI inventory;
- CLI command and envelope decision;
- event representation decision;
- extension generation and startup-failure decisions;
- public boundary documentation;
- initial visibility and forward-compatibility changes that are safe before the
  freeze.

Exit criteria:

- every candidate stable contract has an owner and class;
- every deprecated or legacy compatibility path has a removal owner and
  absence check;
- required ADR changes are accepted;
- later phase dependencies are resolved;
- no stable promise relies only on an accidental public export.

### Phase H1 — Runtime control and app boundary

Goal: provide a product-neutral, conformance-tested host API.

Scope:

- control capability interfaces and façade;
- versioned IDs, requests, acknowledgements, errors, and cursors;
- session/message/cancellation semantics;
- bounded artifact access;
- local host implementation;
- mock/conformance implementation;
- structured app diagnostics;
- product-neutral embedding example.

H1 includes the minimum client event projection needed to demonstrate
subscription. Full persistence compatibility remains in H2.

Exit criteria:

- a reference host starts a session, sends a message, observes completion,
  handles approval, cancels work, and accesses artifacts using only supported
  APIs;
- the same conformance suite passes for local and mock controls;
- no product-specific adapter exists in the harness.

### Phase H2 — Event, trace, and context contracts

Goal: make observation, replay, resume, and context explanation versioned.

H2 has two explicit workstreams in one phase plan:

```text
H2-A
    canonical event metadata, trace formats, client projections, replay

H2-B
    context diagnostics, captured contributions, persisted context artifacts
```

Scope:

- versioned trace and run-manifest documentation;
- stable typed client event projection;
- stable-v0.1 compatibility readers and fixtures;
- removal of pre-hardening trace, manifest, checkpoint, and context-artifact
  migration branches;
- context diagnostic DTO;
- context determinism and captured-contribution tests;
- replay/continue/resume/branch compatibility.

Exit criteria:

- client timelines do not parse raw internal events;
- compatibility fixtures detect breaking persisted changes;
- context reports explain included, omitted, and dynamic contributions;
- H2-A and H2-B can be reviewed independently.

### Phase H3 — Configuration and CLI stability

Goal: make configuration and selected automation commands dependable.

Scope:

- v0.1 config contract and layering;
- removal of TOML harness config parsing, fallback, seeding, and migration;
- `UNSUPPORTED_LEGACY_CONFIG` detection and error reporting;
- removal of deprecated config aliases from Rust types and JSON Schema;
- section stability labels;
- schema/version rejection behavior;
- provenance diagnostics;
- selected stable command table;
- chosen JSON envelope and error/exit behavior;
- normalized snapshots.

Exit criteria:

- unknown config fields and unsupported versions fail clearly;
- known legacy harness config files fail with `UNSUPPORTED_LEGACY_CONFIG`
  without being parsed or migrated;
- deprecated config aliases are absent from the Rust model and JSON Schema;
- stable commands have tested JSON and exit-code contracts;
- secret provenance never exposes secret values;
- no no-op migration command is added.

### Phase H4 — Extension minimum stability

Goal: make the accepted extension foundation safe without expanding the
ecosystem.

Scope:

- component-level stability matrix;
- manifest-V2-only and Lifecycle-Protocol-V2-only documentation;
- removal of manifest/protocol V1 parsing, conversion, component variants,
  builder methods, activation paths, and adapters;
- removal of deprecated extension Rust APIs and broad deprecation allowances;
- structured host construction and activation reports;
- required/optional failure behavior;
- integrity-aware trust diagnostics;
- canonical tool-path conformance;
- generation pinning as decided by ADR;
- V2 manifest and lifecycle conformance fixtures;
- explicit manifest/protocol V1 rejection fixtures.

Exit criteria:

- expected extension failures do not panic embedders;
- absent or V1 manifest versions are rejected before activation;
- no V1 conversion or legacy-process component path remains;
- required security components fail closed;
- failed reload preserves the active generation;
- built-in, command, extension, and MCP tool origins pass equivalent
  policy/approval/trace tests.

## 22. v0.1 Release Criteria

Gestalt v0.1 is ready when:

- [ ] Stable execution invariants are documented and test-covered.
- [ ] The pre-hardening v0.1 compatibility cutoff is recorded by ADR-031.
- [ ] The greenfield removal ledger is complete with no unclassified legacy or
      deprecated compatibility paths.
- [ ] Legacy harness TOML files fail with `UNSUPPORTED_LEGACY_CONFIG` and are
      never parsed or migrated.
- [ ] Deprecated config aliases are absent from Rust types and JSON Schema.
- [ ] Extension manifest/protocol V1 is rejected and its compatibility
      implementation is removed.
- [ ] Production code exposes no pre-hardening `#[deprecated]` API and carries
      no broad `allow(deprecated)`.
- [ ] Pre-hardening persisted-format compatibility and migration branches are
      removed.
- [ ] Stable Rust exports and SPIs are explicitly enumerated.
- [ ] Product-neutral runtime control and mock conformance exist.
- [ ] No product-specific adapter is required inside the harness.
- [ ] Client events do not expose raw runtime event enums.
- [ ] Trace, run, and required context formats are versioned.
- [ ] Context projection is deterministic for declared and captured inputs.
- [ ] `gestalt.json` version 1 and layering are documented and tested.
- [ ] Selected stable CLI commands have tested JSON and exit behavior.
- [ ] Expected extension activation failures do not panic library consumers.
- [ ] Required extension security components fail closed.
- [ ] All tool origins share the canonical policy and audit path.
- [ ] Documentation authority and lifecycle are defined in `docs/README.md`.
- [ ] `docs/v0.1/` contains only implemented, test-backed contracts.
- [ ] Active domain specs no longer rely on removed crate boundaries.
- [ ] Active docs and fixtures do not advertise or accept removed
      pre-hardening behavior.

## 25. Final Recommendation

Do not make Gestalt v0.1 broader. Make its guarantees explicit and its public
surface smaller.

The v0.1 promise should be:

> Gestalt is a product-neutral, embeddable, policy-aware Rust harness with a
> stable host boundary, deterministic and explainable context, canonical tool
> authority, and versioned audit contracts. Products provide workflows and
> presentation around it.
