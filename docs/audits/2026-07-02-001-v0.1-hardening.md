# Gestalt v0.1 Hardening Audit & Remediation Goal

## Purpose

This document is the execution goal for finishing Gestalt `v0.1` hardening.

The target is **not** to make Gestalt the most feature-rich harness, the best coding agent, the best remote runner, or the most advanced agent framework. The target is narrower and more important:

> Ship a reliable, product-neutral, extensible Rust agent harness with stable-enough protocols, API contracts, runtime boundaries, and conformance tests so future products can safely build on top of it.

Gestalt v0.1 should be a dependable harness substrate. It should provide stable primitives for:

* embedding;
* runtime control;
* session/run lifecycle;
* policy and approval;
* trace and replay;
* context reporting;
* configuration;
* CLI automation;
* extension activation;
* product-neutral app services.

It should avoid feature creep. Do not add Workbench, cloud workers, marketplaces, multi-tenant SaaS, visual workflow builders, or advanced orchestration in this pass. Those should build on top of v0.1 after this hardening work is complete.

---

## Current Branch Context

Branch under review:

```text
v0.1-hardening
```

The branch already made meaningful progress:

* versioned `RuntimeControlV1` DTOs and narrow control traits exist;
* `LocalControlHost` and `MockControlHost` pass shared conformance tests;
* `gestalt.json` v1 schema is stricter;
* legacy TOML config is rejected rather than silently migrated;
* app services have structured report/diagnostic types;
* context build report scaffolding exists;
* trace envelopes are versioned;
* extension V2 manifest validation is stricter;
* extension trust is moving toward integrity pins;
* documentation now has authority rules and a v0.1 contract map.

However, the branch is not yet done. The current state is better described as:

```text
v0.1 hardening foundation: strong
stable runtime-control contract: defined, but not fully wired to real runtime
config hardening: near ready
CLI automation: mostly ready
extension V2 cleanup: promising, unfinished
context diagnostics: promising, unpublished
trace/client event contracts: partial
public runtime API boundary: too broad
```

---

## Desired End State

By the end of this task, Gestalt v0.1 should satisfy these criteria.

### 1. Product-neutral harness core

Gestalt must not assume any one product surface.

The same core/runtime should be usable by:

* CLI;
* TUI;
* future Workbench;
* embedded SDK clients;
* test harnesses;
* future remote workers.

No stable v0.1 API should expose assumptions that only make sense for a CLI or local coding-agent UI.

### 2. Stable-enough protocol and API contracts

Stable v0.1 contracts should exist only where the implementation and tests enforce them.

Published v0.1 contracts must be backed by:

* concrete DTOs;
* stable serialization;
* conformance tests;
* integration tests where relevant;
* documentation matching actual behavior.

Unfinished contracts must remain marked as unpublished, proposed, or under development.

### 3. Real runtime embedding boundary

The v0.1 runtime control API must not only be an in-memory conformance model.

It must be possible for a client to control a real Gestalt runtime session through the stable control interface:

```text
start session
submit/continue message
run model/provider turn
stream/poll events
handle approval
execute policy-checked tool call
produce artifact
persist trace
inspect run/session
cancel running work
```

### 4. Narrow public API surface

`gestalt-runtime` should expose a deliberate stable surface.

Internal implementation details should not accidentally become public compatibility promises.

### 5. Trace and client event separation

The persisted trace can remain lossless and internal-rich.

Client-facing events must be stable, redacted, versioned, and product-neutral.

### 6. Context report correctness

Context diagnostics should be deterministic, bounded, replay-aware, and honest about redaction.

Do not call something “redacted” if raw content is persisted.

### 7. Extension safety and V2 clarity

V2 should be the only active extension manifest/protocol path for v0.1.

Trust, activation, grants, permissions, and runtime generation changes must be deterministic and test-backed.

# Workstream 1 — Runtime Control: Replace Conformance-Only Host With Real Runtime Adapter

## Problem

`RuntimeControlV1` is the most important v0.1 embedding contract, but the current `LocalControlHost`/`MockControlHost` path is mostly an in-memory control model.

That is useful for DTO and behavior conformance, but it is not enough for a real embedding boundary. A product embedding Gestalt needs a control API that can actually drive a real `AgentRuntime` or `RuntimeHost`.

## Goal

Implement a real runtime-backed control implementation.

Suggested naming:

```rust
RealRuntimeControlHost
RuntimeBackedControlHost
AgentRuntimeControlHost
```

Keep the current in-memory host if useful, but name it honestly:

```rust
InMemoryControlHost
MockControlHost
ConformanceControlHost
```

Avoid implying that the in-memory host is the real local runtime control plane.

## Required Behavior

The runtime-backed host must support at least:

```text
start_session
continue_session
submit_message
cancel_run
inspect_session
inspect_run
list_sessions
list_runs
poll_events
list_pending_approvals
respond_to_approval
get_policy_projection
list_artifacts
describe_artifact
read_artifact_range
inspect_runtime
```

For v0.1, it does not need advanced branching or perfect long-running orchestration, but it must not lie. If a feature is not implemented against real runtime semantics, return a stable `UNAVAILABLE`, `VALIDATION`, or documented unsupported error instead of faking behavior.

## Key Implementation Requirements

### Session ownership

Introduce a real session registry for runtime-backed control.

It should track:

```text
SessionIdV1 -> logical session state
RunIdV1 -> physical run state
RunIdV1 -> cancellation handle
RunIdV1 -> trace path / artifact path
SessionIdV1 -> active run
SessionIdV1 -> event cursor source
```

### Real execution

A call to `continue_session` should be able to drive a real runtime turn using:

```text
AgentRuntime
AgentLoop
Provider
ToolCatalog
PolicyEngine
ApprovalProvider
TraceSink
```

For tests, use fake provider and fake tools.

### Event source

`poll_events` must be able to read real events from the runtime-backed event stream or persisted trace.

Do not only return synthetic `SessionStarted` or `MessageQueued` events.

### Cancellation

`cancel_run` must signal the actual running execution if it is active.

Cancellation must:

* mark the run terminal;
* stop queued input acceptance where applicable;
* preserve already committed trace history;
* avoid rewriting committed events;
* return `cancelled: false` for already-terminal runs.

### Artifacts

Artifact APIs must point to actual runtime artifact storage for real runs.

For in-memory tests, the artifact store can remain memory-backed.

### Approval

Approval APIs must bridge to the actual approval broker/provider used by runtime execution.

If full approval bridging is too large, introduce the minimal control-plane adapter needed for one policy-confirmed tool call integration test.

## Required Tests

Add a real runtime-control integration suite in addition to the current conformance tests.

Minimum fixtures:

```text
runtime_control_start_and_complete_fake_provider_run
runtime_control_streams_or_polls_real_events
runtime_control_policy_requires_approval_then_executes_tool
runtime_control_cancel_active_run
runtime_control_artifact_lifecycle_uses_real_artifact_store
runtime_control_idempotency_does_not_duplicate_execution
runtime_control_concurrent_continue_rejects_or_queues_deterministically
```

The same generic conformance suite should run against:

```text
MockControlHost
InMemoryControlHost
RuntimeBackedControlHost
```

## Acceptance Criteria

* Published embedding/runtime-control docs refer to the real runtime-backed host, not only the in-memory host.
* The in-memory host is clearly documented as conformance/test support.
* A fake provider/tool integration test proves real execution through `RuntimeControlV1`.
* Workbench or future SDK can use `RuntimeControlV1` without depending on CLI internals.

# Workstream 2 — Public API Boundary: Narrow `gestalt-runtime`

## Problem

`gestalt-runtime` currently exposes many implementation modules and re-exports internal types. This makes accidental dependencies likely and weakens the v0.1 compatibility story.

`AgentRuntimeBuilder` also exposes public fields, which makes its internals part of the de facto API.

## Goal

Define a deliberate stable v0.1 public API surface.

## Required Changes

### 1. Create a stable API namespace

Introduce a namespace such as:

```rust
gestalt_runtime::api::v1
```

or keep stable items under:

```rust
gestalt_runtime::control
gestalt_runtime::embedding
gestalt_runtime::config
```

but document exactly which modules are stable.

### 2. Reduce crate-root re-exports

Review every `pub mod` and `pub use` in:

```text
crates/gestalt-runtime/src/lib.rs
```

Classify each as:

```text
stable
experimental
internal
test-support
```

Prefer not to expose:

```text
activation internals
event bus internals
extension activation internals
registry builders
runtime snapshots
session queue internals
tool planner internals
workspace context internals
orchestration internals
permission helper internals
```

unless they are intentionally part of the v0.1 extension/embedding contract.

### 3. Make builder fields private

Change `AgentRuntimeBuilder` public fields to private fields where possible.

Expose builder methods for supported configuration only:

```rust
provider(...)
tools(...)
assembler(...)
policy(...)
approval(...)
trace_sink(...)
config(...)
hooks(...)
extension_package(...)
workspace_context_snapshot(...)
build()
```

Avoid allowing clients to mutate internals directly.

### 4. Add compile-fail or API tests

Add tests or checks proving removed/broad APIs are not accidentally exported.

If compile-fail tests are too heavy, use rustdoc/public API snapshot tooling or targeted tests.

## Acceptance Criteria

* `gestalt-runtime` has a clearly documented v0.1 public surface.
* Internal modules are not accidentally presented as stable.
* `AgentRuntimeBuilder` is controlled through methods, not public fields.
* Docs tell embedders which APIs are stable and which are internal/experimental.
* Existing CLI/app code compiles using stable or crate-internal APIs as appropriate.

# Workstream 3 — Trace, Event, and Client Projection Contracts

## Problem

Trace work improved, but client event projection still reuses `TraceEvent`, which exposes too many internal core/runtime structures.

Also, conversion between `AgentEvent` and `TraceEvent` currently depends on serde round-tripping and can panic if the shapes diverge.

## Goal

Separate event representations:

```text
AgentEvent            internal runtime event
TraceEventV1          persisted lossless/audit event
ClientEventPayloadV1  stable product-facing event
```

## Required Changes

### 1. Keep lossless trace internal-rich

`TraceEventV1` may include enough information to support replay, debugging, audit, and internal recovery.

It may contain internal references if documented as trace schema rather than client API.

### 2. Add stable client event payload

Create:

```rust
ClientEventPayloadV1
ClientEventRecordV1
```

Client events should be stable, redacted, and product-neutral.

They should not expose raw:

```text
SessionMessage
ContextProjectionState
TokenBudget
Message
QueuedSessionMessage
ToolNameMapping
HistoryRange
internal failure structs
raw provider request internals
```

unless explicitly stabilized.

### 3. Add event projection function

Add a fallible or total projection function:

```rust
impl TryFrom<&EventEnvelope> for ClientEventRecordV1
```

or:

```rust
fn project_client_event(envelope: &EventEnvelope) -> ClientEventRecordV1
```

### 4. Replace panic conversions

Replace `expect("trace event mirrors agent event")` style conversions with fallible conversion where appropriate.

If a conversion truly cannot fail, prove it through tests and keep the panic out of user-facing paths.

### 5. Unknown event behavior

Trace reader behavior can skip unknown events if documented, but client event projection should preserve forward compatibility:

```text
unknown event kind -> ClientEventPayloadV1::Unknown { kind }
```

or a stable unknown payload.

## Required Tests

Add tests:

```text
trace_event_round_trip_known_events
trace_reader_rejects_bad_schema_version
trace_reader_skips_or_preserves_unknown_event_as_specified
client_event_projection_redacts_internal_context
client_event_projection_does_not_expose_checkpoint_payload
client_event_projection_preserves_order_session_run_turn_seq
agent_to_trace_conversion_is_non_panicking_or_tested
```

## Acceptance Criteria

* Persisted trace and client events are separate contracts.
* `ClientEventRecordV1` no longer exposes raw `TraceEvent`.
* UI/product clients can consume events without depending on runtime internals.
* Replay/internal trace remains useful.

# Workstream 4 — Context Build Reports, Determinism, and Redaction

## Problem

`ContextBuildReportV1` is a good foundation, but the capture method currently implies redaction while storing raw content. This is dangerous for a stable harness.

Context diagnostics are also marked unpublished, so do not publish until semantics are real and tested.

## Goal

Make context reports deterministic, bounded, replay-aware, and honest about content capture/redaction.

## Required Changes

### 1. Fix naming or behavior

Choose one:

#### Option A — Actual redaction

Keep the name `capture_redacted`, but implement real redaction before storing content.

Redact at minimum:

```text
API keys
tokens
Authorization headers
common secret patterns
.env style values
provider credentials
keychain refs if accidentally present
```

#### Option B — Honest naming

Rename to something like:

```rust
capture_bounded
capture_unredacted_for_replay
capture_for_replay
```

Then clearly document that content may be raw and should only be enabled under explicit durability/replay policy.

### 2. Add capture policy

Introduce or enforce capture modes:

```text
disabled
hash_only
redacted
full_for_replay
```

Default should be conservative:

```text
hash_only or redacted
```

Do not default to full raw capture.

### 3. Enforce aggregate bounds

The existing per-contribution and aggregate bounds are good. Keep them and add tests for:

```text
single contribution exceeds bound
aggregate capture exceeds bound
hash mismatch on replay
```

### 4. Determinism

Ensure report ordering is deterministic:

```text
sources sorted by ordering key
omissions sorted deterministically
pipeline_id stable for same inputs
```

### 5. Persistence behavior

Durability modes should be explicit:

```text
disabled -> no report persisted
best_effort -> warning/diagnostic on failure
required -> hard failure on persistence failure
```

## Required Tests

Add tests:

```text
context_report_hash_only_does_not_store_raw_content
context_report_redacted_capture_removes_secrets
context_report_full_capture_requires_explicit_policy
context_report_replay_integrity_detects_tampering
context_report_source_order_is_deterministic
context_report_persistence_required_fails_on_write_error
context_report_best_effort_emits_diagnostic
```

## Acceptance Criteria

* No method name implies redaction unless redaction occurs.
* Context reports do not leak secrets by default.
* Context diagnostics remain unpublished until tests pass.
* Docs accurately describe capture modes and durability.

# Workstream 6 — CLI Automation Contract

## Problem

CLI JSON output has a stable envelope, but warnings/diagnostics are not fully wired through. CLI automation should be stable enough for scripts and future Workbench backend use.

Finalize stable machine-readable CLI behavior.

All stable commands that support JSON should return:

```json
{
  "schema_version": 1,
  "status": "success | error",
  "kind": "...",
  "data": {},
  "error": null,
  "warnings": []
}
```

Errors should include:

```json
{
  "code": "...",
  "message": "...",
  "retryable": false,
  "details": null,
  "correlation_id": null
}
```

### 3. Wire diagnostics to warnings

If app services return diagnostics, CLI JSON should include them in `warnings` or a documented `diagnostics` field.

Do not always emit empty warnings if warnings exist upstream.

### 4. Stable command matrix

Define which commands are stable in v0.1.

Suggested stable set:

```text
config validate
config show --format json
providers list --format json
providers inspect --format json
models list --format json
models inspect --format json
connect
runs list --format json
runs inspect --format json
trace inspect --format json

extension validate
```

Any unstable command should be marked experimental.

### 5. Snapshot tests

Keep snapshot tests for JSON output and text output where applicable.

## Required Tests

```text

cli_json_warnings_include_app_diagnostics
cli_text_output_remains_human_readable
```

## Acceptance Criteria

* CLI output is scriptable.

# Workstream 7 — Extension V2, Trust, Activation, and Permissions

## Problem

Extension hardening is promising but not complete. V2-only behavior, trust rules, activation generation, and permission enforcement need to be test-backed and documented.

## Goal

Make extension V2 safe enough for v0.1 as a harness extension substrate.

## Required Changes

### 1. V2-only manifest

Ensure only `manifest_version = 2` is accepted.

Reject V1 examples and V1 compatibility paths from active docs.

### 2. Manifest validation

Keep strict validation for:

```text
package id
reserved namespace
component id
duplicate component id
entrypoint requirements
client product descriptor
command tool description
command tool input_schema
command tool risk
command tool read_only
command tool idempotent
```

### 3. Trust pins

Trust should require exact package ID plus manifest hash.

Bare trusted entries should not silently normalize to current discovered hash.

### 4. Untrusted activation

Decide final v0.1 behavior for:

```text
extensions.allow_untrusted
```

Recommended:

* keep it only as dev/experimental;
* require explicit configured instances for untrusted activation;
* never auto-activate all discovered packages just because `allow_untrusted = true`;
* emit a diagnostic when untrusted activation is used.

### 5. Extension instances

Configured instances should be deterministic:

```text
instance id -> package id
enabled flag
component enable/disable map
config
grants
```

If all components are disabled, return a clear error.

### 6. Permission enforcement

Permission/grant checks must cover:

```text
workspace read
workspace write
shell
network
allowed paths
MCP stdio
MCP HTTP
process-backed tools
```

### 7. Generation and snapshot

Extension activation should produce deterministic generation/snapshot changes.

Runtime generation changes must not race with an active assistant/tool turn.

## Required Tests

Add or confirm:

```text
extension_network_permission_checked
extension_path_permission_checked
extension_mcp_stdio_permission_checked
extension_mcp_http_permission_checked
extension_generation_snapshot_changes_deterministically
```

## Acceptance Criteria

* V2 is the only active extension protocol for v0.1.
* Untrusted extensions cannot accidentally activate.

Make policy and approval stable enough for embedding clients.

```text
Sandbox
Local
Remote
```

```text
Confirm
Yolo
Human
DryRun
Replay
```

Rename DTO type to:

```rust
ExecutionBackendV1
```

Approval contract must handle:

```text
requested
listed
approved
denied
edited
expired
cancelled
duplicate response
always allow for session
```

```text
tool identity
risk ceiling
input hash or editable scope
matched rule
policy source
```

```text
tool does not execute before approval
approval response resumes execution
edited input changes executed input
```

```text
approval_requested_for_confirm_policy
```

# Workstream 9 — Artifact Access Contract

## Problem

Artifact APIs exist and enforce some bounds, but need real runtime store integration and stronger security semantics.

## Goal

Make artifact access stable, bounded, and safe.

## Required Changes

### 1. Real artifact store

Wire artifact APIs to actual runtime artifact storage for runtime-backed control.

Artifact display paths must be logical display paths, not trusted filesystem paths.

Reject:

```text
../
absolute paths
backslashes on cross-platform paths where they imply traversal
empty path
control characters
```

### 3. Bounded reads

Keep maximum chunk size.

Also validate:

```text
offset conversion
length conversion
offset + length overflow
range past EOF
zero-length behavior
```

### 4. Metadata

Artifact metadata should include:

```text
logical_id
display_path
size
media_type
integrity/hash
```

If media type detection is not implemented, document default behavior.

### 5. Cross-session isolation

A session must not read another session’s artifact.

## Required Tests

```text
artifact_create_rejects_traversal
artifact_create_rejects_absolute_path
artifact_read_rejects_oversized_chunk
artifact_read_rejects_offset_overflow
artifact_read_rejects_range_past_eof
artifact_cross_session_access_denied_or_not_found
artifact_integrity_matches_content
artifact_real_runtime_tool_output_materialized
```

## Acceptance Criteria

* Runtime-backed artifacts work.
* Artifact access is bounded and isolated.
* Display path is never treated as an authority-bearing filesystem path.

```text
severity
code
message
correlation_id
details
```

```text
provider resolution warnings
skill trust errors
extension rejection diagnostics
config warnings
auth resolution warnings
```

where relevant.

### 5. Workbench readiness without building Workbench

The app layer should be good enough for Workbench later, but do not build Workbench now.

## Required Tests

```text
app_report_success_contains_value_no_error
```

unstable extension trait supplies the limited first-party registry/event
inspection needed by `gestalt-app` and integration tests.

## Workstream 3 — Trace and Client Event Contracts

The persisted event type is now explicitly `TraceEventV1`. It remains
internal-rich for replay and recovery, while `ClientEventRecordV1` contains the
separate `ClientEventPayloadV1` product projection. Client payloads omit raw
checkpoint history, projection state, token budgets, messages, queued
messages, tool mappings, history ranges, provider request hashes, artifact
paths, working directories, and internal failure structures.

`project_client_event_line` preserves envelope ordering metadata and maps
unknown future trace kinds to `ClientEventPayloadV1::Unknown`. CLI JSON tailing
uses this forward-compatible projection. Known text is redacted again during
projection. Core-agent/trace conversions now implement fallible `TryFrom` in
both directions; the former serde `expect` conversions were removed.

`trace_contract_tests` now covers known round trips, bad schema versions,
documented unknown trace handling, unknown client projection, checkpoint
omission, redaction, metadata ordering, and non-panicking conversion. Strict
workspace Clippy and both full feature test matrices passed. The wire contracts
and privacy distinction are published in `docs/v0.1/trace-events.md`.

## Workstream 4 — Context Reports and Capture Safety

Context report capture is now controlled by
`ContextManagementPolicy::capture` with `disabled`, `hash_only`, `redacted`,
and `full_for_replay` modes. The default is `hash_only`; raw replay content is
stored only when `full_for_replay` is selected explicitly.

`CapturedContributionV1` records original and captured hashes/sizes separately.
Hash-only records contain no content. Redacted records apply redaction to plain
text and serialized JSON, covering API keys, tokens, authorization headers,
`.env` assignments, provider credentials, keychain references, common provider
token prefixes, JWT-like values, and credential-bearing URLs. Report loading
validates stored content and full replay validates original content integrity.

Report construction sorts captures, sources, and omissions deterministically,
rejects duplicate captures and mode mismatches, and enforces the 256 KiB
per-source and 1 MiB aggregate bounds. Disabled, best-effort, and required
durability behavior have direct tests. The generated `gestalt.json` schema and
full fixture include the capture policy.

The 12-test context report contract suite, 21 context-management integration
tests, strict workspace Clippy, and both full workspace feature matrices pass.
The contract is published in `docs/v0.1/context-build-report.md` and exposed
through `gestalt_runtime::api::v1`.

# Codex Operating Instructions

When implementing this goal:

1. Do not start by refactoring broadly.
2. First map current code paths and tests.
3. Preserve working behavior unless it conflicts with v0.1 contract correctness.
4. Prefer small, reviewable commits by domain.
5. Do not add new product features.
6. Do not silently keep legacy compatibility unless explicitly documented as supported.
7. If a contract is not implemented, mark it unpublished rather than faking stability.
8. Add tests before declaring any contract published.
9. Keep terminology precise:
   * policy mode is not execution backend;
   * trace event is not client event;
   * in-memory conformance host is not real runtime control;
   * raw capture is not redaction.
10. Optimize for reliability, explicitness, and future extension.

The final result should make Gestalt v0.1 a stable foundation that later Workbench, remote workers, enterprise workflow packs, and cloud runners can build on without depending on unstable internals.
